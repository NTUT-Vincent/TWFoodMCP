# TWFoodMCP Trust and Classification Policy

**Status:** Normative  
**Applies to:** OKF source documents, draft submissions, validation pipelines, runtime KV documents, MCP responses, crawlers, importers, and human review  
**Last updated:** 2026-08-01

This document is a normative supplement to `docs/MVP_SPEC.md`. When an implementation detail is ambiguous, this policy governs trust, lifecycle, source authority, data quality, calculation eligibility, and access classification.

## 1. Core rule: classifications are independent axes

TWFoodMCP must not collapse different meanings into one `level`, `score`, or manually authored `trust_tier`.

Every record is evaluated on separate axes:

1. **Lifecycle** — whether the document is draft, stable, or deprecated.
2. **Verification trust** — derived from the OKF `verified` actors.
3. **Source authority** — what kind of evidence supports each claim.
4. **Food data quality** — completeness, confidence, freshness, and whether deterministic calculation is allowed.
5. **Access classification** — who is permitted to read the data.

A high value on one axis does not imply a high value on another. For example, a document can be human-reviewed but still contain only partial nutrition data.

---

## 2. Lifecycle

Every TWFoodMCP OKF document must explicitly declare one of:

```yaml
status: draft | stable | deprecated
```

Rules:

- `draft`: not available in the public runtime dataset; not searchable by normal public tools; not usable in nutrition calculation.
- `stable`: eligible for the public runtime dataset after all promotion requirements pass.
- `deprecated`: preserved for history and revision tracing; excluded from default search and calculation.
- The OKF default behavior for an omitted status must not be relied on. TWFoodMCP validation rejects documents without an explicit `status`.
- Crawlers, importers, agents, and public submitters may create only `draft` documents.
- Only the fixed review-and-merge pipeline may promote a document to `stable`.

---

## 3. Verification trust is derived, never self-declared

### 3.1 Canonical derivation

The build pipeline derives runtime trust from the OKF `verified` array:

```text
unverified         no verified entries
machine-confirmed  verified entries exist, but none are human:* actors
human-reviewed     at least one authorized human:* actor verified this exact document revision
```

Example:

```yaml
generated:
  by: process:7eleven-crawler
  at: 2026-08-01T00:30:00+08:00

verified:
  - by: process:schema-validator
    at: 2026-08-01T00:31:00+08:00
```

This is `machine-confirmed`.

```yaml
verified:
  - by: process:schema-validator
    at: 2026-08-01T00:31:00+08:00
  - by: human:dietitian-001
    at: 2026-08-01T10:00:00+08:00
```

This is `human-reviewed` only when `human:dietitian-001` is an authorized reviewer and actually reviewed the exact revision.

### 3.2 Prohibited behavior

Source OKF documents and draft submissions must not accept a user-authored field such as:

```yaml
trust_tier: human-reviewed
```

The following actors must never create a `human:*` verification entry:

- crawlers
- CI jobs
- schema validators
- LLMs
- AI agents
- scheduled jobs
- import scripts
- anonymous contributors

A nutritionist or other expert being the author of an external post does not automatically make the TWFoodMCP document `human-reviewed`. The expert must review the TWFoodMCP document itself, and the pipeline must record that review.

### 3.3 Runtime representation

`trust_tier` may exist in Cloudflare KV runtime documents and MCP responses for efficient filtering and ranking, but it must be generated by the build pipeline from `verified`. It is derived output, not source-of-truth input.

## 4. Source authority

Each source should carry a canonical `source_class`:

```yaml
sources:
  - id: official-product-page
    resource: https://example.com/product
    title: Official product page
    author: organization:example
    source_class: primary_official
```

Allowed values:

```text
primary_label            physical package or menu label
primary_government       government dataset or official government publication
primary_official         brand, restaurant, retailer, or manufacturer official publication
verifiable_secondary     distributor page or dated, identifiable package evidence
expert_interpretation    registered professional's interpretation or explanation
third_party_dataset      external structured dataset without primary authority
community_submission     user-contributed text, photo, or report pending verification
estimated_or_untraceable estimate, AI inference, memory, or untraceable claim
```

Mapping to the source levels in `docs/MVP_SPEC.md`:

- Level A: `primary_label`, `primary_government`, `primary_official`
- Level B: `verifiable_secondary`
- Level C: `expert_interpretation`, `third_party_dataset`
- Level D: `community_submission`, `estimated_or_untraceable`

Rules:

- Source authority applies to individual claims, not automatically to the entire document.
- A primary source may still be incomplete, stale, or ambiguous.
- An expert interpretation is not a replacement for a package label, official nutrition table, or government dataset.
- Conflicting sources must be preserved and surfaced for review; the pipeline must not silently choose the most convenient value.
- Untraceable values must never be promoted as factual nutrition values.

## 5. Food data quality

Use the existing `quality` object. The canonical shape is:

```yaml
quality:
  data_quality: official_brand
  completeness: partial
  confidence: medium
  calculation_allowed: true
```

### 5.1 `data_quality`

Allowed source-quality values remain:

```text
official_label
official_brand
government_database
verified_community_label
third_party_database
community_report
estimated
```

### 5.2 `completeness`

Canonical values:

```text
minimal             identity or a small number of facts only
partial             some nutrition, serving, ingredient, or allergen fields are known
nutrition_complete  all nutrition fields presented by the source have been captured with a clear basis
full_label          identity, serving, nutrition, ingredients, allergens, and revision evidence are captured when available
```

`completeness` describes captured coverage, not truth or authority.

### 5.3 `confidence`

Canonical values:

```text
high
medium
low
```

Rules:

- `high` normally requires a primary source, clear product identity and basis, and human review.
- `medium` may be used for clear official web data or verifiable secondary evidence with remaining limitations.
- `low` applies to third-party, estimated, ambiguous, incomplete, or not-yet-reviewed claims.
- Human review does not automatically make confidence `high`.

### 5.4 `calculation_allowed`

`calculation_allowed: true` means deterministic arithmetic is permitted only for nutrient values that are explicitly present and have a clear basis.

It may be true for a partial record when all of the following are true:

- product identity is sufficiently resolved;
- serving or nutrition basis is explicit;
- the published value is directly supported by evidence;
- no unsupported unit conversion is required;
- the value is not an estimate presented as fact.

Missing nutrients remain unknown and must never become zero.

`calculation_allowed` must be false when:

- serving or basis is ambiguous;
- the number is estimated or inferred;
- ml-to-g conversion would require an unknown density;
- the source cannot be traced;
- product version identity is unresolved;
- the record is draft or deprecated.

## 6. Freshness and staleness

Freshness is independent of trust and source authority.

Rules:

- `stale_after` should be explicit whenever the data can change.
- Stale stable data may remain queryable only with a prominent warning and reduced ranking.
- Stale data must not silently override a newer revision.
- Stale allergen, ingredient, or formulation information requires an especially prominent warning.
- Human review does not remove staleness; a new verification event or revision is required.

---

## 7. Access classification

Optional metadata:

```yaml
access:
  classification: public
```

Allowed values:

```text
public
internal
restricted
confidential
```

Rules:

- Access classification is not a trust score.
- YAML metadata alone does not enforce access control.
- Enforcement must occur through repository permissions, Cloudflare bindings, MCP authentication, and runtime authorization.
- Only `public` records may enter the public KV dataset.
- Personal health data, precise location, identity numbers, addresses, phone numbers, medication data, and private submissions must not enter the public food knowledge dataset.

## 8. Special handling of crawlers and imports

Crawler/import output must start as:

```yaml
status: draft

generated:
  by: process:<crawler-or-importer-id>
  at: <timestamp>

verified:
  - by: process:schema-validator
    at: <timestamp>
```

Rules:

- Crawling an official page establishes source authority, not human review.
- A crawler must preserve the source URL, retrieval timestamp, and raw evidence or reproducible snapshot reference.
- Missing fields must remain absent or explicitly unknown.
- The crawler must not infer ingredients, allergens, weight, barcode, or nutrition basis.
- Website layout changes or parse uncertainty must send records to review rather than publishing them.
- A deterministic import from a government dataset may be machine-confirmed, but TWFoodMCP currently still requires human review before stable publication unless a future policy explicitly approves a specific importer and dataset version.

---

## 9. Special handling of nutritionist and social-media sources

Nutritionist, dietitian, doctor, trainer, or other professional social-media content is classified as:

```yaml
source_class: expert_interpretation
```

Rules:

- It may provide explanation, context, portion guidance, cautions, or a lead for further verification.
- It must not overwrite primary factual fields when a package label, official page, or government source is available.
- A post's nutrition numbers require their own traceable primary evidence before becoming stable facts.
- Store a link and a concise, original summary unless reuse rights explicitly permit copying the content.
- Do not copy entire captions, images, or infographics without permission.
- Do not convert disease-specific advice into general product safety claims.
- The professional's external authorship does not create `human-reviewed`; only review of the exact TWFoodMCP revision does.

## 10. Stable promotion matrix

A record may become stable only when all general requirements pass and one acceptable evidence path is met.

General requirements:

- explicit `status` transition through the review pipeline;
- schema validation;
- resolved identity and duplicate/revision checks;
- at least one traceable source;
- authorized human review;
- explicit quality and calculation flags;
- no unresolved high-risk allergen, unit, basis, or product-version conflict.

Acceptable evidence paths:

1. Level A source plus authorized human review.
2. Clear, dated, identifiable package/menu evidence plus authorized human review.
3. Two independent Level B sources plus authorized human review.
4. Approved government deterministic import plus schema validation and authorized human review.

Level C or D evidence alone must not become stable factual nutrition data.

## 11. Runtime build rules

The GitHub OKF files are the source of truth. During build and publication:

1. Reject missing or invalid explicit lifecycle status.
2. Derive `trust_tier` from `verified`.
3. Validate source classes and quality fields.
4. Publish only eligible `stable`, `public` documents.
5. Exclude drafts and deprecated records from the default public index.
6. Preserve unknown nutrient fields as missing values.
7. Preserve source, revision, verification, quality, freshness, and limitation metadata.
8. Apply deterministic ranking modifiers for trust and staleness without hiding the underlying evidence.
9. Write versioned KV documents and manifest first.
10. Update `dataset:current` only after all versioned writes complete successfully.

## 12. Non-negotiable examples

### Official webpage captured by crawler

```yaml
status: draft
generated:
  by: process:7eleven-crawler
verified:
  - by: process:schema-validator
sources:
  - source_class: primary_official
quality:
  data_quality: official_brand
  completeness: partial
  confidence: medium
  calculation_allowed: true
```

Runtime trust: `machine-confirmed`. It is still a draft and must not enter the public dataset.

### Same document after authorized review

```yaml
status: stable
verified:
  - by: process:schema-validator
  - by: human:reviewer-001
```

Runtime trust: `human-reviewed`. Missing nutrition fields still remain unknown.

### Nutritionist Instagram post

```yaml
status: draft
sources:
  - source_class: expert_interpretation
quality:
  data_quality: third_party_database
  completeness: minimal
  confidence: low
  calculation_allowed: false
```

The post may be retained as interpretation or a verification lead, but it cannot independently establish stable product nutrition facts.

---

## 13. Change control

Changes to canonical enum values, stable promotion requirements, trust derivation, or access rules require:

- an explicit specification update;
- migration notes for existing OKF and KV documents;
- validation and runtime tests;
- human review through a pull request.

Implementations must not introduce new trust levels or silently change the meaning of existing levels without updating this policy.
